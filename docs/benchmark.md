## 해석과 확인하지 못한 것

- 처리량은 워커 수에 따라 늘어난다. 연결 수가 워커 수를 넘으면 큐에서 기다리는 시간 때문에 지연이 급증하고,
  연결 500에서는 2초 안에 응답을 못 받는 요청이 수백 건 나온다(연결 하나에 워커 하나 구조의 한계, README "한계").
- 각 조합은 **1회만** 측정했다. 리버스 프록시 워커 16, 연결 10의 1,789 req/s처럼 추세에서 벗어난 값이 있다.
- **첫 측정에서는** 리버스 프록시에 non-2xx가 대량으로 나왔다(예: 워커 16, 연결 10에서 9만여 건). 처음엔 임시 포트
  고갈로 봤지만, 같은 부하를 따로 10초 걸었을 때는 TIME_WAIT 1만9천 개에서도 5만 건이 전부 200이었다.
  이 TIME_WAIT는 먼저 닫는 쪽(백엔드)에 생겨 프록시의 임시 포트를 쓰지 않기 때문이다. 실행 사이에 TIME_WAIT가
  빠지기를 기다리도록 바꾼 이번 측정에서는 non-2xx가 0이다. 첫 측정의 non-2xx가 어떤 상태 코드였는지 기록하지
  않아서 원인은 확정하지 못했다. 그래서 상태 코드별 개수를 남기는 마지막 열을 추가했다.
- 연결 하나(wrk -c1)로 잴 때 중앙값은 약 0.15ms인데 p99가 20~50ms로 튄다. 서버 쪽 Nagle(헤더와 본문을 한 번에
  보내고 TCP_NODELAY를 걸어도 같음), 접근 로그, keep-alive 여부는 원인이 아님을 확인했다. 원인은 찾지 못했다.
  (참고: zsh에서 `&`로 띄운 프로세스는 기본 옵션 BG_NICE 때문에 우선순위가 낮아진다. 측정 스크립트는 bash로
  돌기 때문에 이 영향은 없다.)
