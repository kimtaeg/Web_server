# 설계 문서

각 결정은 "무엇을 / 왜 / 대안과 버린 이유" 순서로 적는다. 단계가 진행될 때마다 추가한다.

## 0. 전체 구조

```
main ─ server(accept) ─▶ threadpool(bounded queue) ─▶ worker: conn_handle(fd)
                                                        │ keep-alive 루프
                                                        ▼
                               http_parser(증분, I/O 없음) ─▶ router
                                                        ├─ static
                                                        ├─ cgi
                                                        ├─ rproxy ─┐
                                                        └─ fproxy ─┴─ upstream (+ cache)
```

## 1. 빌드와 이식성

### OS 차이는 `src/platform.h` 한 곳에만
- **무엇**: `#ifdef __linux__ / __APPLE__`는 이 파일에만 쓴다. 다른 모듈은 `PLATFORM_SEND_FLAGS`,
  `platform_sock_init()` 같은 추상화만 호출한다.
- **왜**: 분기가 여러 파일에 흩어지면 한쪽 OS에서만 깨지는 버그를 찾기 어렵다. 파일 하나만 보면
  두 OS의 차이를 전부 설명할 수 있다.
- `static inline`만 쓰고 `.c`를 두지 않는다. 호출 비용이 없고, "차이 = 헤더 하나"가 유지된다.

### SIGPIPE를 두 겹으로 막기
- 끊긴 소켓에 `send`하면 SIGPIPE가 오고, 기본 동작은 **프로세스 종료**다. 클라이언트 하나가
  연결을 끊는 바람에 서버 전체가 죽으면 안 된다.
- 1겹: main에서 `SIGPIPE`를 `SIG_IGN`으로 설정 (2단계).
- 2겹: 소켓 단위. Linux는 `send(..., MSG_NOSIGNAL)`, macOS는 `MSG_NOSIGNAL`이 없어서
  `setsockopt(SO_NOSIGPIPE)`를 쓴다.
  1겹만 있어도 동작은 하지만, 라이브러리나 테스트가 시그널 설정을 바꿔도 안전하도록 2겹을 둔다.
- 검증: `tests/unit/test_platform.c`는 SIGPIPE를 일부러 기본값으로 두고 닫힌 소켓에 send해서
  EPIPE가 오는지 확인한다. SO_NOSIGPIPE 설정을 빼면 테스트 프로세스가 시그널 13으로 죽는 것도 확인했다.

### 빌드 모드 분리
- `build/{release,debug,asan}/`를 따로 쓴다. 플래그가 다른 `.o`를 섞어 링크하면
  ASan 런타임 불일치 같은 원인 모를 오류가 나기 때문이다.
- `-std=c11 -pedantic`에 `-D_POSIX_C_SOURCE=200809L`을 더하고, OS 확장이 필요한 부분만
  `_DARWIN_C_SOURCE` / `_DEFAULT_SOURCE`로 연다.
- macOS(arm64)의 ASan은 LeakSanitizer를 지원하지 않는다. 누수 검사는 Linux의 `make asan`에서
  하거나, macOS에서는 `leaks --atExit`로 한다.

## 2. 버퍼 (`buf`)

- **상한(max)을 버퍼가 직접 가진다.** 헤더 16KB 초과 → 431, 본문 초과 → 413처럼 "얼마나 쌓였나"가
  곧 오류 정책이기 때문이다. `BUF_ERR_LIMIT`(→ 4xx)와 `BUF_ERR_NOMEM`(→ 500)을 구분해서 돌려준다.
- **실패하면 내용이 바뀌지 않는다.** 일부만 쓰인 상태가 없으므로 호출자의 오류 처리가 단순해진다.
- **용량은 2배씩 늘린다.** append의 분할 상환 비용이 O(1)이 된다. 단, max+1보다 크게 잡지는 않는다.
- **consume은 memmove로 처리한다.** 읽기 오프셋을 두는 링버퍼보다 단순하다. 소비하고 남는 양은
  보통 파이프라이닝된 다음 요청 일부라서 복사 비용이 작다.
- **`buf_find(from)`**: 조각으로 도착할 때마다 처음부터 `\r\n\r\n`을 찾으면 O(n²)이 된다.
  이전에 검사한 길이 − 3부터 다시 찾으면 경계에 걸친 경우도 놓치지 않는다.
  `memmem`은 POSIX가 아니라서 `memchr` + `memcmp`로 직접 구현했다.
- 항상 NUL로 끝나게 유지한다(디버깅·로그용). 데이터는 바이너리여도 괜찮다.

## 3. HTTP 파서 (`http_parser`)

### 버퍼 전체를 넘기고, 다시 시작할 위치를 기억하는 증분 파서
- **무엇**: 파서는 소켓을 직접 읽지 않는다. 호출자는 지금까지 쌓인 버퍼 전체를 매번 넘기고,
  파서는 `pos`(어디까지 봤나)와 상태(START → REQLINE → HEADERS → BODY → DONE)를 기억했다가
  새 바이트부터 이어서 본다.
- **왜 I/O를 분리했나**: 파서가 소켓에 의존하지 않으므로 바이트 배열만으로 단위 테스트할 수 있다.
  "1바이트씩 넣기" 같은 분할 테스트를 소켓 없이 결정적으로 돌릴 수 있는 것도 이 때문이다.
  같은 파서를 업스트림 응답 처리나 다른 이벤트 모델에서도 재사용할 수 있다.
- **왜 바이트 단위 상태 기계가 아닌가**: 줄 단위로 처리하면 코드가 훨씬 짧고, `memchr`로
  `'\n'`을 찾는 부분은 이미 증분이다(`pos`부터만 찾는다). 전체 비용은 O(n)이다.
- **오프셋으로 저장**: 버퍼가 realloc되면 주소가 바뀐다. 그래서 파싱 중에는 오프셋만 저장하고,
  `PARSE_OK` 시점에 `data + offset`으로 포인터를 만든다. 파서 안에서 malloc은 0번이다.
- **파이프라이닝**: `*consumed`는 이 요청이 차지한 바이트 수다. 호출자가 `buf_consume` 하면
  다음 요청이 버퍼 앞에 남는다.

### 분할 무관성: 어떻게 쪼개 넣어도 같은 결과
TCP는 경계를 보존하지 않는다. 같은 요청이 한 번에 오든 1바이트씩 오든 결과(오류 코드 포함)가
같아야 한다. 이를 지키는 규칙은 세 가지다.
1. 완성된 줄은 도착하는 즉시 순서대로 처리한다. 앞줄의 오류가 항상 먼저 보고된다.
2. 요청줄은 `scan_reqline` 하나가 왼쪽에서 오른쪽으로 검사한다. 줄이 아직 끝나지 않았을 때도
   같은 함수를 쓰고, 끝에 다다르면 "더 필요"로 멈출 뿐이다.
   대상 문자열 안에서는 **길이 검사(414)를 문자 검사(400)보다 먼저** 한다. 순서가 반대면
   9000번째 바이트의 제어문자 때문에 한 번에 넣으면 400, 쪼개 넣으면 414가 된다.
3. 줄 끝(LF 앞의 CR)은 줄의 가장 오른쪽이므로 **가장 마지막에** 검사한다.

**증명 방법**: 테스트 하네스가 모든 케이스를 한 번에, 1바이트씩, 시드를 고정한 무작위 분할 5가지로
넣고 결과 전체를 문자열로 바꿔 비교한다. 여기에 무작위 변형 입력 2000개를 더했다.
규칙 2나 3을 일부러 깨 보면 테스트가 실패하는 것도 확인했다.

### 상한은 줄이 끝나기 전에도 판정
끝없이 보내는 요청줄이나 헤더로 메모리를 고갈시키는 공격을 막기 위해, 상한(414, 431)을 넘는
순간 줄 끝을 기다리지 않고 오류를 낸다. 413은 Content-Length를 보는 시점, 즉 본문이 도착하기
전에 판정한다.

### 오류 정책과 그 이유
| 상황 | 응답 | 이유 |
|---|---|---|
| CL과 TE가 함께 있음 | 400 | 프록시와 백엔드가 본문 경계를 다르게 읽으면 요청 스머글링이 된다. 어느 쪽을 믿을지 고르지 않고 거부한다 |
| `Transfer-Encoding: chunked` | 411 | chunked 요청 본문은 지원하지 않는다. RFC 9110이 허용하는 "길이를 달라"는 응답이다 |
| obs-fold, bare LF, `Host :` | 400 | 관대하게 받아 주면 해석이 갈리는 지점(스머글링 벡터)이 생긴다. 엄격하게 거부한다 |
| 값이 다른 CL 중복 | 400 | 값이 같은 중복은 RFC 9110이 허용하므로 받는다 |
| 소문자 메서드 `get` | 501 | 메서드는 대소문자를 구분한다 (RFC 9110 9.1) |
| 405 | 파서가 아닌 router | 허용 여부가 경로에 따라 다르기 때문이다 |

판정 우선순위: 요청줄(메서드 → 대상 → 버전) → 헤더 줄(순서대로) → 헤더 끝에서 CL+TE(400) →
Host(400) → TE(411) → CL 없는 POST/PUT/PATCH(411) → CL 상한(413).

### keep-alive
HTTP/1.1은 기본적으로 유지하고 `Connection: close`면 끊는다. HTTP/1.0은 `Connection: keep-alive`일
때만 유지한다. `Connection` 값은 쉼표로 구분된 토큰 목록으로 파싱하고(대소문자 무시), `close`가
항상 우선한다. `closed`나 `keep-alivex`처럼 토큰이 정확히 일치하지 않으면 무시한다.

## 4. MIME (`mime`)
- 정적 const 테이블을 선형 탐색한다. 항목이 수십 개라 해시는 과하다. 읽기 전용이라 락도 필요 없다.
- 마지막 경로 구성요소의 마지막 `.`을 확장자로 본다. 그래서 `a.b/c`나 숨김 파일 `.bashrc`는 기본값이 된다.
- 텍스트 계열에는 `charset=utf-8`을 붙인다. 브라우저가 인코딩을 추측하지 않게 하기 위해서다.

## 5. 동시성 모델 (`server`, `threadpool`)

### main 스레드는 accept만, 워커 N개가 처리
- **무엇**: main 스레드는 `poll(500ms)` → `accept` → `threadpool_try_submit`만 한다.
  읽기, 파싱, 응답은 전부 고정 N개의 워커가 맡는다.
- **왜 연결마다 스레드를 만들지 않나**: 접속이 폭주하면 스레드 수가 무한히 늘어나
  메모리와 스케줄링이 무너진다. 워커 수를 고정하면 자원 사용량에 상한이 생긴다.
- **왜 큐에 상한을 두나**: 큐가 가득 차면 accept 직후 **503 + `Retry-After`**로 빠르게 거절한다
  (load shedding). 큐가 무한하면 모든 요청이 성공하는 것처럼 보이지만 지연이 끝없이 늘어난다.
- **503은 블록하지 않고 보낸다**: main 스레드가 응답을 읽지 않는 클라이언트에 막히면 서버 전체가
  멈춘다. 그래서 fd를 `O_NONBLOCK`으로 바꾸고 한 번만 send한 뒤 닫는다.
  처음에는 `MSG_DONTWAIT`를 썼는데, macOS의 AF_UNIX 소켓에서는 이 플래그가 무시되어 블록하는
  것을 테스트(`test_netio`)가 잡아냈다. 그래서 POSIX 표준 방식으로 바꿨다.

### bounded queue: mutex 1개 + cond 2개
| 이름 | 보호 대상 / 쓰임 |
|---|---|
| `mu` | 원형 버퍼(`q, head, count`)와 `shutting_down` |
| `not_empty` | 워커가 할 일이 생길 때까지 기다린다. 생산자가 push한 뒤 signal한다 |
| `not_full` | `submit_wait`가 자리가 날 때까지 기다린다. 워커가 pop한 뒤 signal한다 |

- 기다리는 조건이 둘(큐가 비었다 / 가득 찼다)이므로 cond도 둘이다. 하나로 합치면 broadcast로
  상관없는 쪽까지 깨워야 해서 불필요한 깨어남(thundering herd)이 생긴다.
- 기다릴 때는 `if`가 아니라 `while`로 조건을 다시 확인한다. 가짜 깨어남(spurious wakeup)과
  다른 워커가 먼저 가져간 경우를 모두 막기 위해서다.
- 작업 함수는 **락 밖에서** 실행한다. 한 연결 처리가 오래 걸려도 다른 워커를 막지 않는다.
- main은 `try_submit`(즉시 실패)을 쓴다. accept 루프는 절대 기다리면 안 되기 때문이다.
  `submit_wait`는 표준 bounded buffer의 짝으로 제공하고 단위 테스트로 검증한다.

## 6. 연결 수명 (`conn`)
- **keep-alive 루프**: 파싱 → 핸들러 → `buf_consume(used)` 순서로 돈다. 버퍼에 남은 바이트가
  다음 요청이므로 파이프라이닝이 자연스럽게 처리된다.
- **유휴 타임아웃(기본 5초)**: recv 한 번을 기다리는 최대 시간이다. 요청 사이에 아무것도 오지 않는
  연결을 닫는다. 대기는 250ms 단위로 나눠서 하고 그때마다 종료 플래그를 확인한다. 덕분에 종료할 때
  유휴 연결을 최대 5초씩 기다리지 않는다.
- **헤더 마감(기본 10초, 7단계에서 추가)**: 요청의 첫 바이트부터 헤더 끝(빈 줄)까지 허용하는 **총** 시간이다.
  넘기면 408을 보내고 닫는다.
  - **정정**: 2단계에서는 "유휴 타임아웃만으로 slowloris도 막힌다"고 적었는데, **틀린 설명**이었다.
    유휴 타이머는 바이트가 하나 올 때마다 다시 시작되므로, 헤더를 4초마다 1바이트씩 보내면 영원히
    끊기지 않는다. 워커가 8개뿐이므로 그런 연결 8개면 서버가 멈춘다.
  - 마감 시각은 다시 시작되지 않는다. 그래서 이 문제를 막는다. 단위 테스트는 마감을 끈 경우(0)에
    3초 동안 응답이 없는 것까지 보여 줘서, 방어가 없을 때의 문제를 재현한다.
- **`SO_SNDTIMEO`(10초)**: 응답을 읽지 않는 클라이언트가 워커를 영원히 붙잡지 못하게 한다.
- **파싱 오류가 나면 무조건 close**: 요청 경계를 잃었으므로 같은 연결로는 더 진행할 수 없다.
- **lingering close**: 아직 읽지 않은 입력이 남은 상태에서 바로 close하면 TCP가 RST를 보낸다.
  그러면 클라이언트가 직전에 받은 오류 응답을 읽기도 전에 버릴 수 있다. 그래서
  `shutdown(SHUT_WR)` → 남은 입력을 잠깐 비움 → close 순서로 닫는다.
- **핸들러는 함수 포인터**로 받는다. 지금은 `static_handle`이 들어가고, router가 생기면
  router가 그 자리를 대신한다. conn은 응답 내용을 모른다.

## 7. 정적 파일 (`static`)

### 루트 탈출 방어는 두 겹
1. **문자열 단계 (순수 함수, 단위 테스트)**: 퍼센트 디코딩을 한 뒤 `//`, `.`, `..`를 정규화한다.
   `..`가 루트 위로 올라가면 403이다.
   - **순서가 중요하다.** 디코딩 → 정규화 순서여야 `%2e%2e`가 `..`로 바뀐 뒤 판정된다.
   - `%00`은 400으로 거부한다. C 문자열을 중간에서 잘라 검사를 우회하는 데 쓰이기 때문이다.
2. **파일시스템 단계**: `realpath`로 심볼릭 링크까지 푼 실제 경로가 루트 아래인지 다시 검사한다.

둘 중 하나만으로는 부족하다.
- 1만 있으면 "루트 안에 있는 링크가 밖을 가리키는" 경우를 잡지 못한다.
- 2만 있으면 루트 밖의 **존재하지 않는** 경로에서 `realpath`가 ENOENT로 실패해 404가 나간다.
  그러면 "탈출 시도 = 403"이라는 정책을 지킬 수 없다.

포함 관계 검사는 단순 접두사 비교로 하면 `/var/www`가 `/var/www2`를 포함한다고 오판한다.
그래서 접두사 다음 글자가 `\0`이나 `/`인지까지 확인한다.

### 그 밖의 결정
- **TOCTOU**: `realpath`로 확인한 뒤 open하기 전에 경로가 링크로 바뀔 수 있다. 마지막 구성요소는
  `O_NOFOLLOW`로 막는다. 그 다음 `fstat`으로 일반 파일인지(FIFO나 장치 파일이 아닌지) 확인한다.
- **디렉터리**: `/docs`로 요청하면 `/docs/`로 301을 보낸다. 그래야 index.html 안의 상대 링크가
  올바르게 풀린다. index.html이 없는 디렉터리는 403이다(목록을 보여주지 않는다).
- **전송**: 64KB 고정 버퍼로 `read` → `send_all`을 반복한다. 파일 크기와 상관없이 메모리 사용량이
  일정하다. sendfile을 쓰지 않으므로 OS별 분기도 없다.
  전송 도중 파일이 줄어들면 약속한 Content-Length를 채울 수 없으므로 연결을 끊어서 알린다.
- **HEAD**: GET과 같은 헤더(같은 Content-Length)를 보내고 본문은 보내지 않는다.

## 8. 종료, 시그널, 로그

### 시그널 핸들러는 플래그만 세운다
- SIGINT와 SIGTERM이 오면 `volatile sig_atomic_t g_stop = 1` 한 줄만 실행한다.
- **왜**: 핸들러는 메인 코드가 어느 지점에 있든 끼어든다. 예를 들어 malloc이나 로그 락을 잡고
  있는 도중일 수도 있다. 그 상태에서 핸들러가 같은 락을 잡거나 free를 부르면 교착이나 힙 손상이
  생긴다. 그래서 async-signal-safe한 일(플래그 대입)만 하고, 실제 정리는 메인 흐름이 한다.
- `sigaction`을 `SA_RESTART` 없이 등록한다. 블록 중인 시스템 콜이 EINTR로 깨어나 플래그를 보게 하기 위해서다.
- **accept 루프는 `poll(500ms)`로 기다린다.** "플래그 확인 → accept 진입" 사이에 시그널이 오면
  EINTR이 나지 않고 다음 연결이 올 때까지 잠들 수 있다. poll 타임아웃이 이 경쟁 조건을 덮는다.
- **SIGPIPE**는 두 겹으로 막는다: 프로세스 전체에 `SIG_IGN`을 걸고, 소켓마다
  `MSG_NOSIGNAL`(Linux) 또는 `SO_NOSIGPIPE`(macOS)를 쓴다 (1절).

### graceful shutdown 순서
| 단계 | 하는 일 | 이 순서인 이유 |
|---|---|---|
| 1 | 리슨 소켓 close | 새 연결을 더 받지 않는다 |
| 2 | 큐 close (`threadpool_close`) | submit을 막고 잠든 워커를 전부 깨운다(broadcast). 블록하지 않는다 |
| 3 | 진행 중 요청 완료 | 워커는 처리 중인 요청과 **큐에 이미 들어온 연결**까지 끝낸다. keep-alive로 대기 중인 연결은 250ms 안에 플래그를 보고 닫는다 |
| 4 | join (`threadpool_join_free`) | 모든 워커가 끝나야 공유 자원을 쓰는 스레드가 없어진다 |
| 5 | 자원 해제 | 4 이후에만 큐·mutex·cond를 free해도 안전하다. 순서를 바꾸면 워커가 해제된 mutex를 잡는다(use-after-free) |

- 큐에 남은 연결을 버리지 않고 처리한다. 이미 accept한 연결이므로, 버리면 클라이언트는 이유 없이 끊긴 것처럼 보인다.
- `threadpool_join_free`는 안전장치로 내부에서 close를 한 번 더 부른다(close는 멱등).
  close를 빠뜨려도 워커가 끝나지 않아 영원히 join하는 일이 없다.

### 접근 로그
```
2026-11-20 11:34:00.359 [INFO] 127.0.0.1 "GET /big.bin HTTP/1.1" 200 500162B 2ms
```
- 시간, IP(`getpeername` + `inet_ntop`, IPv4/IPv6), 요청줄, 상태, 보낸 바이트, 처리 시간을 남긴다.
  파싱 오류로 요청줄을 알 수 없으면 `"-"`로 쓴다.
- **스레드 안전성**: 전역 mutex 하나로 "한 줄 쓰기"를 통째로 직렬화한다. stdio의 내부 락은 호출
  단위라서, 여러 번 호출해 한 줄을 만들면 그 사이에 다른 스레드가 끼어든다. 8개 스레드 × 300줄로
  줄이 섞이지 않음을 테스트한다.
- 시간은 `localtime_r`로 구한다. `localtime`은 정적 버퍼를 공유해서 스레드 안전하지 않다.
- 대상 경로는 256바이트에서 자른다. 파서가 출력 가능한 ASCII만 허용하므로 로그 주입(개행 삽입)은 불가능하다.

### 검증
- **중간 끊김 (`tests/func/abort.sh`)**: 워커 1개, 유휴 타임아웃 30초로 띄운다. nc로 헤더 일부나
  본문 일부만 보내고 끊기, 즉시 끊기, 빈 연결을 합쳐 60번 만든 직후 curl이 바로 200을 받는지,
  `lsof`로 센 fd 개수가 처음과 같은지 확인한다.
  EOF를 무시하도록 일부러 고친 바이너리에서는 503과 fd 누수(8개 → 12개)로 실패하는 것도 확인했다.
- **누수 (`make leakcheck`)**: 서버 실행 → 정상, 오류, keep-alive, 중간 끊김, 유휴 연결 → SIGINT.
  - macOS(arm64)의 ASan은 LeakSanitizer가 없다. 그래서 `leaks --atExit`(debug 빌드)로 누수를 보고,
    같은 시나리오를 ASan 빌드로 돌려 메모리 오류를 확인한다.
  - Linux에서는 ASan + LSan 하나로 둘 다 확인한다.
  - `buf_free` 하나를 지운 바이너리에서 `11 leaks for 112640 total leaked bytes`로 실패하는 것도 확인했다.

## 9. 라우팅과 CGI (`router`, `cgi`)

### router
- 경로 접두사 규칙 중에서 **가장 길게 일치하는** 것을 고르고, 없으면 기본 핸들러(static)로 보낸다.
- 접두사는 경로 구성요소 경계에서만 일치한다. `/cgi-bin`은 `/cgi-bin/x`와는 일치하지만
  `/cgi-binx`와는 일치하지 않는다.
- conn은 핸들러를 함수 포인터 하나로만 알고, 그 자리에 router가 들어간다. conn 코드는 바뀌지 않았다.
- 매칭은 디코딩 전 원본 경로로 한다. 그래서 `/cgi%2dbin/x`는 static으로 간다. 이게 안전한 이유는
  **CGI 디렉터리를 문서 루트 밖**에 두기 때문이다. 그러면 static이 CGI 실행 파일을 그대로
  내려보내는 일이 구조적으로 불가능하다. 안에 두면 시작할 때 경고를 남긴다.

### 스크립트 결정
- `/cgi-bin/<이름>`의 이름은 경로 구성요소 하나이고 `[A-Za-z0-9._-]`만 허용한다(맨 앞 `.` 금지).
- `%`를 아예 허용하지 않으므로 디코딩으로 우회하는 공격이 성립하지 않는다. `..`, `/`, `%2e%2e`는
  모두 404다.

### fork / exec — 멀티스레드 프로세스에서
- **fork는 호출한 스레드만 복제한다.** 다른 스레드가 잡고 있던 락(malloc 내부, 로그 mutex)은 자식에서
  영원히 풀리지 않는다. 그래서 자식은 exec 전까지 async-signal-safe 함수만 쓴다
  (`setpgid`, `sigaction`, `dup2`, `chdir`, `execve`, `_exit`).
  argv, envp, sigaction 구조체, 작업 디렉터리 문자열은 **fork 전에 부모가** 만든다.
- **CLOEXEC**: 다른 워커가 동시에 fork하면 그 순간 열려 있던 fd가 전부 CGI로 복제된다. 클라이언트
  소켓이 새면 CGI가 끝날 때까지 그 연결이 닫히지 않는다. 그래서 리슨 소켓, 클라이언트 소켓, 정적 파일,
  CGI 파이프 모두에 CLOEXEC를 건다. 다만 macOS에는 `accept4`가 없어서 accept 직후 `fcntl`로 걸어야
  하고, 그 사이에 다른 스레드가 fork하는 아주 짧은 틈은 남는다.
- **SIGPIPE 복원**: 서버가 무시(SIG_IGN)하던 시그널은 exec 후에도 "무시"로 상속된다. 그래서 자식에서
  기본값으로 되돌린다.
- **환경 변수**: 서버 자신의 환경은 넘기지 않는다(비밀 값 유출 방지). CGI에 필요한 변수만 명시적으로
  만든다: RFC 3875 변수 7개와 `GATEWAY_INTERFACE`, `SERVER_SOFTWARE`, `PATH`.

### 입출력: 교착 방지
- POST 본문을 다 쓴 다음에 출력을 읽으면, 출력을 먼저 많이 쓰는 CGI와 서로의 파이프 버퍼(64KB)가 차서
  영원히 기다린다. 그래서 두 파이프를 non-blocking으로 두고 **한 poll 루프에서 쓰기와 읽기를 함께** 한다.
  1MB를 넣고 1MB를 받는 단위 테스트로 검증한다.
- CGI가 본문을 읽지 않고 끝나면 write가 EPIPE로 실패한다. 이때 stdin만 닫고 출력은 계속 받는다.
  이 동작은 프로세스가 SIGPIPE를 무시하고 있어야 성립한다. 파이프에는 `MSG_NOSIGNAL`이 없다.

### 타임아웃과 좀비
- 자식은 `setpgid(0,0)`으로 자기 프로세스 그룹을 만든다.
  - 타임아웃이 나면 `kill(-pgid, SIGKILL)`로 **그룹 전체**를 죽인다. 셸 스크립트가 띄운 손자 프로세스가
    살아남으면 파이프를 붙잡고 있기 때문이다.
  - 터미널에서 누른 Ctrl+C가 CGI에 직접 전달되지도 않는다(포그라운드 그룹이 아니므로).
- stdout이 EOF여도 프로세스는 아직 살아 있을 수 있다(stdout을 닫고 나서 잠드는 CGI). 그래서 블로킹
  `waitpid` 대신 마감 시각까지 `WNOHANG`으로 확인한다.
- **모든 경로에서 `waitpid(pid)`를 정확히 한 번** 부른다. 그래서 좀비가 남지 않는다. `waitpid(-1)`이 아니라
  pid를 지정하므로 다른 워커의 자식을 가로채지 않는다.
- 결과 매핑: 타임아웃 → 504. 종료 코드가 0이 아니거나 시그널로 죽었거나 exec에 실패했거나(127)
  출력 형식이 틀리면 → 500.
- **검증**: `waitpid`를 빼먹은 바이너리에서는 기능 테스트가 "좀비 1개"로 실패한다.

### 출력 → 응답
- 출력 전체를 버퍼에 모은다(상한 8MB). Content-Length를 서버가 계산하기 때문에 keep-alive가 그대로 유지된다.
- CGI 헤더를 다음과 같이 해석한다.
  - `Status:`는 응답 상태 코드로 쓴다.
  - `Location`만 있으면 302다.
  - `Content-Type`도 `Location`도 없으면 500이다.
  - `Connection`, `Content-Length`, `Date`, `Server`는 서버가 정하므로 CGI가 보낸 것은 버린다.
  - 헤더 값에 CR 같은 제어문자가 있으면 500이다(응답 분할 방지).
- 헤더와 본문을 **한 번의 send**로 보낸다. 작은 write를 두 번 하면 Nagle과 지연 ACK가 겹쳐 두 번째
  조각이 수십 ms 늦게 나갈 수 있다.

## 10. 설정과 리버스 프록시 (`config`, `upstream`, `rproxy`)

### 설정
- 우선순위는 **기본값 < 설정 파일(`-f`) < 명령줄 옵션**이다. 같은 바이너리를 설정 파일 하나로 띄우되,
  테스트할 때는 포트만 명령줄로 바꿀 수 있다.
- 형식은 줄 단위 지시어다. 오류는 `line 7: 알 수 없는 지시어 'rout'`처럼 **줄 번호**와 함께 알려 준다.
  파싱은 순수 함수(`config_parse_string`)라서 파일 없이 단위 테스트한다.
- `route [host=<이름>] <prefix> <host:port>...`
  - 선택 순서: **경로 접두사가 가장 긴 규칙**이 먼저다. 길이가 같으면 Host 조건이 있는 규칙이 이긴다.
  - Host는 포트를 떼고 대소문자 무시로 비교한다.
  - 백엔드 주소는 시작할 때 `getaddrinfo`로 한 번 풀어 둔다(요청마다 DNS 조회하지 않음).

### 업스트림 연결
- **non-blocking connect + poll**: blocking connect는 OS 기본 타임아웃(수십 초)까지 워커를 붙잡는다.
  `EINPROGRESS` 뒤 `poll(POLLOUT)`으로 기다리고, `SO_ERROR`로 성공·실패를 확인한다. 연결된 뒤에는
  blocking으로 되돌리고, 읽기는 `recv_some`(poll 타임아웃)으로, 쓰기는 `SO_SNDTIMEO`로 시간을 제한한다.
- **업스트림 연결은 요청 하나로 끝낸다**(`Connection: close`, 커넥션 풀 없음). 그래서 "업스트림 EOF =
  응답 끝"이라는 단순한 규칙을 쓸 수 있다. 대가는 요청마다 TCP 핸드셰이크 한 번이다.
  커넥션 풀은 개선 후보로 남긴다.

### 요청 재작성
- **hop-by-hop 헤더 제거**(RFC 9110 7.6.1): Connection, Keep-Alive, Proxy-\*, TE, Trailer,
  Transfer-Encoding, Upgrade, 그리고 **`Connection:` 헤더에 이름이 적힌 헤더**.
  이 헤더들은 "이 한 구간의 연결"에만 의미가 있다. 그대로 넘기면 예를 들어 클라이언트의 keep-alive
  요청이 백엔드 연결 정책을 바꿔 버린다.
- `Expect`도 뺀다. 프록시는 본문을 이미 다 받은 상태라서 100-continue가 의미 없다.
- **추가하는 헤더**
  - `X-Forwarded-For`: 기존 값 뒤에 클라이언트 IP를 **덧붙인다**. 앞단에 프록시가 더 있어도 체인이 보존된다.
  - `X-Forwarded-Proto: http`: 클라이언트가 보낸 값은 덮어쓴다. 클라이언트가 이 값을 위조하지 못하게 하기 위해서다.
  - `Via: 1.1 cweb`: 기존 Via 체인 뒤에 덧붙인다.
- **유지**: Host와 경로(접두사를 떼지 않음). HTTP/1.0 요청에 Host가 없으면 백엔드 주소를 Host로 넣는다.
- 재작성한 결과를 **우리 파서로 다시 파싱하는** 단위 테스트를 둔다. 프록시가 잘못된 HTTP를 만들지 않는다는 보증이다.

### 응답 중계 (스트리밍)
- 상태줄과 헤더만 파싱하고(1xx 중간 응답은 버림), hop-by-hop 헤더를 지운 뒤 **클라이언트 쪽 `Connection`**을
  붙인다. 본문은 16KB 버퍼로 받는 즉시 흘려보낸다. 그래서 응답이 아무리 커도 메모리 사용량은 일정하다.

| 백엔드 응답 | 처리 | 클라이언트 연결 |
|---|---|---|
| Content-Length 있음 | 정확히 그 길이만 중계, 넘치는 바이트는 버림 | **유지** |
| 길이 정보 없음 | 업스트림 EOF까지 중계 | 닫음 (그래야 클라이언트가 끝을 안다) |
| chunked | 바이트를 그대로 통과 | 닫음. HTTP/1.0 클라이언트면 502 |
| HEAD 요청 / 204 / 304 | 본문 없음 (HEAD는 백엔드가 준 CL을 유지) | 유지 |
| 헤더를 다 받기 전 타임아웃 | 아직 아무것도 안 보냈으므로 **504** 페이지 | 유지 |
| 헤더를 다 받기 전 EOF, 형식 오류, 101 | **502** | 유지 |
| 본문 도중 실패 | 헤더가 이미 나갔으므로 상태를 바꿀 수 없음 | **끊어서** 응답이 잘렸음을 알림 |

- 응답 쪽 파서는 bare LF를 허용하는 등 요청 파서보다 관대하다(백엔드는 운영자가 고른 서버다).
  다만 CL이 서로 다르게 두 번 오거나, chunked로 끝나지 않는 TE처럼 **길이를 오해할 수 있는 경우**는
  엄격하게 502로 처리한다. 응답 스머글링을 막기 위해서다.

### 로드밸런싱과 장애 처리
- **라운드로빈**: `atomic_fetch_add(&rr, 1) % n`에서 시작해, down이 아닌 첫 백엔드를 고른다.
  락이 없다. 8개 스레드 × 30000회를 동시에 골라도 백엔드 3개에 **정확히 80000씩** 분배되는 것을
  단위 테스트로 확인한다(카운터가 원자적이지 않으면 이 수치가 어긋난다).
- **down 표시**: 연결에 실패하면 `down_until_ms = now + down_secs`를 `atomic_store`로 쓴다. 단조 시계를
  쓰므로 벽시계가 바뀌어도 영향이 없다. 기간이 지나면 자동으로 다시 후보가 된다(수동 헬스체크 없음).
  두 워커가 동시에 쓰더라도 둘 다 "거의 같은 미래 시각"이므로 어느 값이 남든 결과가 같다.
- **재시도는 연결 단계 실패에서만, 1회**: 요청을 보낸 뒤에 실패한 것을 재시도하면 POST가 두 번 실행될 수
  있다(비멱등). 연결 전이면 백엔드는 그 요청을 본 적이 없으므로 안전하다.
  **읽기 타임아웃은 down으로 표시하지 않는다.** 느린 요청 하나 때문에 정상 백엔드를 빼면 안 되기 때문이다.
- **상태 코드**
  - 풀 전체가 down이면 시도 없이 즉시 502를 보낸다(빠른 실패).
  - 마지막 실패가 연결 타임아웃이면 504, 그 밖의 연결 실패면 502다.
  - 연결한 뒤 응답을 기다리다 시간이 지나면 504다.

### 백엔드 모드와 CGI 헤더
- `--name A`를 주면 모든 응답(정적, CGI, 오류, 503)에 `X-Backend: A`가 붙는다. 같은 바이너리로 로드밸런싱을
  눈으로 확인하기 위한 기능이다. `getopt_long`은 POSIX가 아니므로 argv에서 직접 꺼낸다.
- CGI에 요청 헤더를 `HTTP_*` 환경 변수로 넘긴다(RFC 3875 4.1.18). 단, **`Proxy` 헤더는 넘기지 않는다**
  (httpoxy, CVE-2016-5385). `HTTP_PROXY` 환경 변수가 생기면 CGI 안의 HTTP 클라이언트 라이브러리가
  이를 자기 프록시 설정으로 읽어, 공격자 서버로 요청을 보내게 된다.

## 11. 포워드 프록시와 캐시 (`fproxy`, `cache`)

### 포워드 프록시
- 요청 대상이 absolute-form(`GET http://host[:port]/path`)이고 `forward_proxy on`이면 fproxy가 처리한다.
  `curl -x` 같은 클라이언트가 프록시에 보내는 형태가 이것이다. router가 경로 규칙보다 **먼저** 이 경우를 가른다.
- `https://` 대상과 `CONNECT`(TLS 터널)는 **501**이다. https를 처리하려면 터널링이나 TLS 종단이 필요한데,
  둘 다 범위 밖이다. 파서는 `https://`를 형식상 받아들이고(`is_https`) 정책 판단은 fproxy에 맡긴다.
  "형식 검사는 파서, 정책은 핸들러"로 역할을 나눈 것이다.
- 대상 주소는 요청마다 `getaddrinfo`로 풀고, **나온 주소를 순서대로** 연결해 본다.
  이 Mac에서 `localhost`는 `::1`이 먼저 나오는데, 원본 서버가 127.0.0.1에서만 대기 중이면 첫 주소는
  연결이 거부된다. 첫 주소만 시도하면 502가 난다(기능 테스트가 `http://localhost:<port>`로 이 경우를 덮는다).
- 업스트림에는 **origin-form**(`/path?query`)으로 바꿔 보낸다. 재작성과 중계는 rproxy와 같은 `upstream.c`를 쓴다.
- **보안**: 포워드 프록시는 아무나 내부망으로 요청을 보낼 수 있는 통로가 된다(open proxy, SSRF).
  그래서 **기본값은 꺼짐**이다.
- **루프 감지**: Via 표식을 인스턴스마다 다르게 둔다(`1.1 cweb-<pid>`). 들어온 요청의 Via에 자기 표식이
  있으면 508이다. 표식이 고정 문자열이면 cweb 앞에 cweb을 둔 정상적인 체인까지 루프로 오판한다.
  실제로 루프가 생기는 곳은 rproxy 라우트가 자기 자신을 가리킬 때라서 rproxy에서도 같은 검사를 한다.

### 무엇을 저장하나 (`fproxy_cacheable`, 순수 함수)
아래를 **모두** 만족할 때만 저장한다. 공유 캐시는 "다른 사람에게 줘도 되는 응답"만 저장해야 하기 때문이다(RFC 9111).

| 조건 | 이유 |
|---|---|
| GET, `Authorization` 없음 | 인증된 응답을 남에게 주면 정보 유출 (3.5절) |
| 200, Content-Length 있음, 끝까지 받음 | 잘린 응답이나 길이를 모르는 응답을 저장하면 다음 사람이 깨진 응답을 받는다 |
| `no-store`, `private`, `no-cache`, `max-age=0`이 아님 | 원본 서버의 지시 |
| `Set-Cookie` 없음 | 한 사용자의 세션 쿠키가 다른 사용자에게 나가는 사고 방지 |
| 값 크기 ≤ 객체 상한 | 큰 파일 하나가 캐시 전체를 밀어내는 것 방지 |

- **TTL**: `s-maxage`가 `max-age`보다 우선하고(공유 캐시 규칙), 둘 다 없으면 `cache_default_ttl_secs`를 쓴다.
  만료 판정에는 단조 시계를 쓴다.
- **키**: 같은 자원의 표기 차이를 하나로 모은다. `http://` + 소문자 host + (`:80`이면 생략) + 경로 + 쿼리.
  경로는 대소문자를 구분하므로 그대로 둔다.
- **사본 뜨기**: `upstream_relay`가 클라이언트로 보내는 바이트를 그대로 사본에도 쌓는다(tee). 단,
  `Connection`과 `X-Cache`처럼 **연결 단위로 달라지는 헤더는 사본에 넣지 않는다.** HIT 응답을 만들 때
  그 연결에 맞게 다시 붙인다.
- 캐시가 켜져 있으면 HIT이 아닌 모든 응답에 `X-Cache: MISS`를 붙인다(POST, 인증 요청 포함).
  HEAD는 캐시된 GET의 헤더로 HIT 처리한다.

### LRU 자료구조
- 해시맵(체이닝, FNV-1a)과 이중 연결 리스트를 함께 쓴다. head가 가장 최근, tail이 다음 축출 대상이다.
  조회, 삽입, 축출, 맨 앞으로 이동이 모두 O(1)이다.
- 항목 하나는 `[entry][key][value]`를 **한 번에 할당**한다. malloc/free 횟수와 단편화가 줄어든다.
- 비용(charge)은 구조체 크기 + 키 + 값이다. 전체가 상한을 넘으면 tail부터 연쇄적으로 축출한다.

### 동기화: rwlock과 LRU의 충돌
LRU는 **읽기(get)도 순서를 바꾸는 쓰기**다. 조회한 항목을 맨 앞으로 옮겨야 하기 때문이다.
그래서 read lock 하나만으로는 정확한 LRU를 지킬 수 없다. get을 두 단계로 나눴다.
1. **read lock**: 찾아서 값을 복사한다. 덩치 큰 memcpy를 여러 스레드가 동시에 할 수 있다.
2. **write lock**: 키로 **다시** 찾아서 맨 앞으로 옮긴다. 포인터 몇 개만 바꾸므로 아주 짧다.

1과 2 사이에 다른 스레드가 그 항목을 축출하거나 교체했을 수 있다. 그래서 1에서 얻은 포인터를 2에서 쓰지
않고 키로 다시 찾는다. 이 규칙을 어기면 해제된 메모리를 건드린다.

put은 malloc과 memcpy를 **락 밖에서** 하고, write lock 안에서는 연결만 바꾼다. 축출된 항목의 free도
락 밖에서 한다. 그래서 write lock을 잡는 시간이 최소다. hits/misses 통계는 read lock 아래에서도 동시에
늘어나므로 원자 변수로 둔다.

대안과 버린 이유:
- mutex 하나만 쓰기: 가장 단순하지만 읽기끼리도 직렬화된다.
- 근사 LRU(원자적 "마지막 사용 시각"만 갱신하고 축출할 때 보정): 읽기는 가장 빠르지만, 축출 순서가
  정확하지 않아 "LRU 순서" 테스트를 근사치로 만들어야 한다.

### 검증
- **LRU 순서**: A, B, C를 넣고 A를 조회한 뒤 D를 넣으면 B가 빠진다.
- **연쇄 축출 경계**: `cache_entry_overhead()`로 항목 비용을 **정확히** 계산해서, "2개를 빼면 넘치고 3개를 빼면
  딱 맞는" 경계를 검사한다. 처음에는 오버헤드를 어림값으로 잡았다가 경계가 맞지 않아 이렇게 바꿨다.
- **동시 접근**: 8개 스레드 × 20000회 get/put/교체를 축출이 계속 일어나는 작은 용량에서 돌린다.
  값은 키에서 정해지는 패턴이라, 찢어진 값이나 다른 키의 값이 나오면 바로 드러난다. 끝난 뒤
  `cache_self_check`로 리스트, 해시, 바이트 합계가 일치하는지 본다.
- **테스트가 실제로 잡는지**
  - 조회 후 맨 앞으로 옮기기를 빼면 LRU 테스트가 실패한다.
  - 옮길 때 write lock을 빼면 ASan이 **5번 중 5번** heap-use-after-free를 보고한다.

## 12. 동시성 모델 비교와 선택 이유

| 모델 | 구조 | 장점 | 단점 |
|---|---|---|---|
| 연결당 프로세스 (fork) | accept할 때마다 fork | 격리가 강하고 단순하다 | fork 비용이 크고 메모리 사용량이 연결 수에 비례한다 |
| 연결당 스레드 | accept할 때마다 pthread_create | 코드가 직관적이다(블로킹 I/O) | 스레드 수에 상한이 없어 폭주하면 무너진다 |
| **스레드 풀 + bounded queue (이 프로젝트)** | 고정 N개 워커, 큐가 차면 503 | 자원에 상한이 있다. 블로킹 코드를 그대로 쓴다. 부하가 넘치면 빨리 거절한다 | **동시에 처리할 수 있는 연결 수 = 워커 수**. 느린 클라이언트가 워커를 붙잡는다 |
| 이벤트 루프 (epoll/kqueue, 단일 스레드) | 논블로킹 소켓 + 준비된 fd만 처리 | 연결 수만 개(C10K)도 가볍다 | 모든 코드가 논블로킹 상태 기계가 되어야 한다. CPU 작업이 루프를 막는다 |
| 하이브리드 (이벤트 루프 + 워커 풀) | I/O 대기는 루프가, 완성된 요청 처리만 워커가 | 유휴·느린 연결이 워커를 차지하지 않는다 | 구현이 가장 복잡하다(연결 상태를 스레드 사이로 넘겨야 함) |

**선택 이유**
- 학습과 면접 설명이 목표인 프로젝트다. 블로킹 I/O로 쓰면 파서, 프록시, CGI의 로직이 **위에서 아래로
  읽히는 코드**가 된다.
- 고정 워커와 bounded queue만으로도 "자원 상한"과 "과부하 시 빠른 거절(503)"이라는 운영상 핵심 성질을 얻는다.
- 파서를 I/O 없는 증분 파서로 만들어 둔 것은 하이브리드로 옮길 때를 대비한 것이다. 이벤트 루프는 받은
  바이트를 버퍼에 쌓고 `http_parse`가 OK를 줄 때만 워커에 넘기면 된다. 파서는 바꿀 필요가 없다.

**한계를 숫자로 확인했다** (`docs/benchmark.md`): 연결 수가 워커 수보다 훨씬 많아지면(-c 500, 워커 16),
나머지 연결은 큐에서 기다리다 타임아웃된다. 연결이 keep-alive로 워커를 붙잡고 있기 때문이다.
헤더 마감(slowloris 방어)은 "워커를 붙잡는 시간"에 상한을 둘 뿐, "워커 수만큼 연결을 열어 두는" 공격을
막지는 못한다(`tests/func/edge.sh`의 slowloris x4가 이를 보여 준다). 다음 단계는 하이브리드다.

## 13. 포워드 프록시 vs 리버스 프록시

| | 포워드 프록시 (`fproxy`) | 리버스 프록시 (`rproxy`) |
|---|---|---|
| 누구 편인가 | **클라이언트** 쪽에 있다. 클라이언트가 프록시를 알고 설정한다 (`curl -x`) | **서버** 쪽에 있다. 클라이언트는 프록시의 존재를 모른다 |
| 요청 형태 | absolute-form `GET http://host/path` | origin-form `GET /path` (평범한 요청) |
| 목적지 결정 | 요청 URL의 host | 프록시 **설정**(route 규칙, Host 헤더) |
| 주된 용도 | 접근 제어, 캐시, 익명화, 사내망 출구 | 로드밸런싱, TLS 종단, 백엔드 은닉, 장애 백엔드 우회 |
| 이 프로젝트의 기능 | getaddrinfo로 대상 해석, LRU 캐시, X-Cache | 라운드로빈, down 표시와 1회 재시도, Host 규칙 |
| 위험 | **open proxy / SSRF** (아무나 내부망으로) → 기본값 꺼짐 | 백엔드를 우회하는 경로 노출, 루프 → Via로 508 |

둘 다 `upstream.c`를 공유한다. 요청 재작성(hop-by-hop 헤더 제거, XFF/Via)과 응답 중계 규칙은 같고,
**목적지를 정하는 방법만 다르다.**

## 15. 테스트
- 외부 라이브러리 없이 `tests/unit/test.h`의 매크로(`CHECK`, `REQUIRE`, `CHECK_EQ_*`)를 쓴다.
- 테스트 파일 하나 = 실행 파일 하나. 크래시나 시그널이 다른 테스트에 번지지 않는다.
  `tests/run_unit.sh`가 종료 코드로 성공/실패를 모은다.
- 러너는 테스트 하나당 60초 워치독을 둔다. 실제로 멈춘 테스트 하나 때문에 `make test` 전체가
  끝나지 않은 적이 있어서 추가했다. 시간을 넘기면 죽이기 직전에 스택(macOS `sample`, Linux `gdb`)을
  남겨서 원인을 추적할 수 있게 한다.
- **valgrind(CI, Ubuntu)**: 판정 기준은 valgrind가 보고한 메모리 오류 0, definitely lost 0이다. valgrind 아래에서만
  나는 기능 검사 실패는 참고용으로 출력한다. 실제로 그런 실패가 하나 있었다. `test_cgi`의 "exec 실패 → `CGI_ERR_EXEC`"
  검사가 valgrind 아래에서는 `CGI_ERR_EXIT`로 나왔다. valgrind가 `execve`를 가로채므로 exec이 실패한 자식의 종료 코드가
  127이 아니게 되기 때문으로 보인다. 같은 테스트는 일반 `make test`(Ubuntu와 macOS)에서 통과한다.
  처음에는 이 실패를 "느려져서 생긴 시간 검사 실패"로 짐작했는데, 로그를 보니 틀린 짐작이었다.
- macOS는 새로 만든 실행 파일을 처음 실행할 때 보안 검사로 0.3~0.5초가 걸린다(실측). 그래서 CGI 테스트는
  "정상 완료를 기대하는 실행"과 "타임아웃을 기대하는 실행"의 시간 제한을 분리했다.
- `make func`는 실제 서버를 빈 포트에 띄우고 curl로 검증한다(`tests/func/*.sh`). keep-alive는
  curl `-v` 문구 대신 버전과 무관한 `%{num_connects}`로 확인한다.
- 타이밍에 민감한 검사(예: "워커가 첫 연결을 잡은 뒤 큐 포화 → 503")는 고정 sleep에 기대지 않고
  `eventually`로 짧게 재시도한다. 고정 sleep을 쓰면 스케줄링에 따라 가끔 실패한다.
